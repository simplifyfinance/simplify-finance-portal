Compliance notes — where every box gets its data

Every box on Needs & objectives and Broker comments, traced field by field to the screen it came from. Code as shipped at 4c895bd.

How a box is written

One model call per box — Claude Sonnet, temperature 0, so the same deal writes the same way twice. Each call receives the facts block (the whole deal, assembled fresh from the fact find every time) followed by that one box's instruction.

The system prompt's first rule is never invent: every number and name in the answer must appear in the facts given. The facts end with a NOT RECORDED list, and the model is told that anything on it is genuinely unknown and must be stated as unknown rather than filled in or written around.

Where the risk sits. The facts block is live and correct. But six of the nine boxes also receive a short context summary of BC fields — a leftover from before the facts block existed. Those two sources can disagree, and nothing decides which wins. That is the single thread running through every HIGH below.

What I would change

1 — Delete the context summary. Every value in it is already in the facts block, live and correct. Keeping both is how a prompt states one thing while the facts state another. analysisComment, borrowingPowerComment and depositComment already run on the facts alone, and they are the three with no HIGH against them. That is not a coincidence.

2 — Stop asking for figures that are never supplied. Maximum borrowing capacity, debt-to-income, and the other lenders' rates and fees. Either pass them or take them out of the instruction — asking for a number the model does not have is how an invented number gets written.

3 — Pass what is already recorded. The security address, and the retirement age and repayment method from the Risks tab. Three boxes ask about things the portal knows and does not hand over.

4 — Split analysisComment. Thirty topics in one call, asking for bold subheadings that arrive as raw markdown. It is the box most likely to pad.
